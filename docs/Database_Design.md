# NetZero Finance - Database Design Document

## Purpose

This document defines the database architecture, collection structure, relationships, and authentication flow for the NetZero Finance platform.

The objective is to establish a clear and scalable data model before implementation begins.

---

# 1. Database Overview

NetZero Finance uses MongoDB as its primary database.

MongoDB was selected because:

* It integrates naturally with JSON-based APIs such as Plaid.
* It provides schema flexibility during rapid product development.
* It works well with Node.js and Express applications.
* It allows efficient storage of transaction and subscription data.

---

# 2. Database Collections

The MVP consists of four primary collections:

1. Users
2. Transactions
3. Subscriptions
4. Insights

---

# 3. Collection: Users

## Purpose

Stores user account information, authentication details, and Plaid integration information.

---

## Fields

| Field            | Type     | Description                                  |
| ---------------- | -------- | -------------------------------------------- |
| _id              | ObjectId | Unique user identifier                       |
| name             | String   | User's full name                             |
| email            | String   | User email address                           |
| password         | String   | Hashed password                              |
| plaidAccessToken | String   | Plaid access token for transaction retrieval |
| createdAt        | Date     | Account creation timestamp                   |
| updatedAt        | Date     | Last update timestamp                        |

---

## Example Document

```json
{
  "_id": "665d1f9e",
  "name": "Anushka Singh",
  "email": "anushka@gmail.com",
  "password": "hashed_password",
  "plaidAccessToken": "access-sandbox-123",
  "createdAt": "2026-06-01",
  "updatedAt": "2026-06-01"
}
```

# 4. Collection: Transactions

## Purpose

Stores all banking transactions imported from Plaid Sandbox.

This collection acts as the raw financial data layer for the application.

---

## Fields

| Field              | Type     | Description                   |
| ------------------ | -------- | ----------------------------- |
| _id                | ObjectId | Unique transaction identifier |
| userId             | ObjectId | Owner of transaction          |
| merchantName       | String   | Merchant name                 |
| amount             | Number   | Transaction amount            |
| category           | String   | Transaction category          |
| transactionDate    | Date     | Date of transaction           |
| plaidTransactionId | String   | Unique Plaid transaction ID   |
| createdAt          | Date     | Record creation timestamp     |

---

## Example Document

```json
{
  "_id": "txn123",
  "userId": "user123",
  "merchantName": "Netflix",
  "amount": 199,
  "category": "Streaming",
  "transactionDate": "2026-06-01",
  "plaidTransactionId": "plaid_tx_12345",
  "createdAt": "2026-06-01"
}
```

---

# 5. Collection: Subscriptions

## Purpose

Stores subscriptions detected by the Subscription Detection Engine.

Subscriptions are not manually created. They are generated automatically from transaction analysis.

---

## Fields

| Field          | Type     | Description                    |
| -------------- | -------- | ------------------------------ |
| _id            | ObjectId | Unique subscription identifier |
| userId         | ObjectId | Owner of subscription          |
| merchantName   | String   | Subscription provider          |
| amount         | Number   | Subscription cost              |
| frequency      | String   | Monthly, Quarterly, Yearly     |
| firstDetected  | Date     | First detection date           |
| lastDetected   | Date     | Most recent detection date     |
| annualCost     | Number   | Estimated annual cost          |
| riskScore      | Number   | Risk score (0-100)             |
| reviewPriority | String   | LOW, MEDIUM, HIGH              |
| status         | String   | Active or Inactive             |

---

## Example Document

```json
{
  "_id": "sub123",
  "userId": "user123",
  "merchantName": "Adobe Creative Cloud",
  "amount": 1675,
  "frequency": "Monthly",
  "firstDetected": "2025-06-01",
  "lastDetected": "2026-06-01",
  "annualCost": 20100,
  "riskScore": 82,
  "reviewPriority": "HIGH",
  "status": "ACTIVE"
}
```

# 6. Collection: Insights

## Purpose

Stores financial recommendations generated by the Insights Engine.

These recommendations help users prioritize subscription reviews.

---

## Fields

| Field               | Type     | Description                           |
| ------------------- | -------- | ------------------------------------- |
| _id                 | ObjectId | Unique insight identifier             |
| userId              | ObjectId | Owner of insight                      |
| title               | String   | Insight title                         |
| description         | String   | Detailed recommendation               |
| type                | String   | Savings, Risk, Duplicate Subscription |
| relatedSubscription | ObjectId | Linked subscription                   |
| createdAt           | Date     | Creation timestamp                    |

---

## Example Document

```json
{
  "_id": "insight123",
  "userId": "user123",
  "title": "Review Adobe Subscription",
  "description": "Adobe Creative Cloud represents 68% of your subscription spending.",
  "type": "Risk",
  "relatedSubscription": "sub123",
  "createdAt": "2026-06-01"
}
```

# 7. Collection Relationships

The platform follows a user-centric architecture.

Each user owns:

* Multiple Transactions
* Multiple Subscriptions
* Multiple Insights

Relationship structure:

User
│
├── Transactions
│
├── Subscriptions
│
└── Insights

---

## Relationship Strategy

MongoDB does not use traditional SQL joins.

Instead, ownership is maintained through:

```text
userId
```

Example:

```json
{
  "userId": "665d1f9e"
}
```

This allows efficient querying of user-specific data.

# 8. Authentication Architecture

The platform uses JWT (JSON Web Token) authentication.

Passwords are never stored in plain text.

Passwords will be hashed using bcrypt before being saved.

---

## Registration Flow

User
↓
Register Form
↓
POST /api/auth/register
↓
Validate Input
↓
Hash Password
↓
Store User
↓
Return Success Response

---

## Login Flow

User
↓
POST /api/auth/login
↓
Verify Email
↓
Compare Password
↓
Generate JWT Token
↓
Return Token

---

## Protected Route Flow

Frontend Request
↓
JWT Token
↓
Authentication Middleware
↓
Verify Token
↓
Allow Access
↓
Return Data

---

# 9. Initial API Endpoints

## Authentication APIs

POST /api/auth/register

Create a new user account.

---

POST /api/auth/login

Authenticate user and return JWT.

---

GET /api/auth/profile

Return authenticated user profile information.
